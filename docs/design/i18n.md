# Design — Internationalization

`apps/web` speaks English (the default and the fallback) and Brazilian Portuguese (`pt-BR`), from one
interface — no separate layouts. The rules are the handoff's (board 05); this page is how they are built.

**Everything technical is still English** (`.claude/rules/rules-global.md`, "Language Standard"):
identifiers, file names, routes, column names, seeded values. Portuguese exists in exactly one place in the
code: `apps/web/lib/i18n/messages/pt-BR.ts` and its siblings below.

## What there is (no dependency)

```
apps/web/lib/i18n/
├── config.ts          LOCALES, DEFAULT_LOCALE, the `oliveira_locale` cookie, Accept-Language parsing
├── translate.ts       createTranslator, formatMessage ({name} variables + a minimal ICU plural)
├── server.ts          getLocale(), getTranslator()        — Server Components and Server Actions
├── provider.tsx       I18nProvider, useT(), useLocale()   — Client Components
├── api-messages.ts    translateApiMessage(message, t)
└── messages/
    ├── en.ts          the shape — common, nav, auth, home, guard, company, pagination, api, shell…
    ├── erp.ts         erpEn + erpPtBR (columns, People, Access profiles, Users, overview)
    ├── table.ts       tableEn + tablePtBR (the shared listing infrastructure)
    ├── pt-BR.ts       typed `Messages` against en.ts — a key missing here fails the typecheck
    └── index.ts       getMessages(locale)
```

The root layout reads the locale on the server (`getLocale()`), sets `<html lang>`, and passes only the
**active** language's catalogue to `I18nProvider` — the other one never ships to the browser.

## Which language

The saved choice (the `oliveira_locale` cookie, set by `setLocaleAction` — one year, `Lax`), else the
browser's `Accept-Language` on a first visit, else English. The switch (`EN | PT`) is on the auth screens
and in the account menu and mobile drawer; it saves the cookie and calls `router.refresh()` so every Server
Component re-renders in the new language without a navigation.

The handoff says the choice is "saved on the user profile". The API has no profile field for it, so it is a
cookie — a backend change (a column and an endpoint) was not made for it.

## Writing a message

- Keys are grouped by domain (`auth.signIn.title`); **a sentence is a whole message with named
  variables** — never concatenated — so a language can reorder it: `'Hello, {name}.'`.
- Plurals use the ICU form the translator implements:
  `'{count, plural, one {# member} other {# members}}'` (`=0 {…}` is supported too).
- **Product and brand names are never in a catalogue.** Pass them as a variable
  (`PRODUCT_LABELS.ERP`, `PLATFORM_NAME`) and mark the text `translate="no"`. They are proper nouns, always
  English.
- Reserve up to +35% in any label that has to fit (a button, a tab, a column header). pt-BR is the longest.
- `useT()` is `t(key, vars?)`; `key` is typed — an unknown key is a compile error, and a missing one at
  runtime renders the key itself, loudly.
- Data tables name their columns by **key** (`labelKey: 'erp.columns.name'`), not by string, so the
  header, the "Customize" list, the export and the active-filter tags all say it in the same language.

### Adding a key

1. Add it to the English catalogue (`en.ts`, or the domain file) — that defines the shape.
2. Add it to the Portuguese one. TypeScript will not let you forget.
3. Use it. If a screen needs more than a handful of keys, give it a domain file like `erp.ts`.

## Messages that come from the API

`apps/api` and `packages/schemas` speak English **contract strings** (`docs/api/http_responses.md`): tests
and clients assert them verbatim, so they never change. The UI shows them in the user's language by looking
each one up — `translateApiMessage(message, t)` — in an exact-match map plus a few patterns that carry a
product or a count (`No licenses left for Oliveira ERP. …`, `3 people deleted`). A message it doesn't know
is shown **as it came**, never swallowed.

It is applied where a message reaches a person: `FormMessage` (every inline field error), the toasts that
show a Server Action's `message`, and `useEntityForm`. When the backend gains a message, add it to
`api-messages.ts` and to the `api.*` group of both catalogues.

## Formatting

Language is not data (handoff § 7): dates and counts follow the **interface** language
(`formatDateMedium(value, locale)`, `formatCount(value, locale)`, `Intl` underneath); currency comes from the
company and a document's format from the data's country, never from the UI language. A date is still read
in UTC — a birthday saved as `1990-01-01` must not become 31 December for anyone west of Greenwich.
`formatDate`/`formatDateTime`/`formatCurrency` in `lib/format.ts` are the legacy pt-BR formatters; new
code uses the locale-aware ones.

## Checking a screen

Open it in both languages at 1440, 1024, 768 and 390px: nothing may overflow or truncate in pt-BR, and
`document.documentElement.lang` follows the switch. A pseudo-locale (+40%, accented) for the end-to-end
suite is in the handoff and is **not** built — the testing phase owns it.
