# 0014 — UUID v7 primary keys, in the tenancy migration

## Context

Primary keys are mixed today: `Person` uses a UUID, and every other table an auto-incrementing
integer. Integer keys are enumerable — with several companies in one database, a sequential id is an
invitation to probe another company's records — and they cannot be generated by a client, which the
field app of a first product (a technician creating records without a connection) will need.
Changing key types later means a second structural migration across every table and foreign key; the
tenancy migration ([0008](0008-multi-tenancy-shared-database.md)) already touches all of them once,
while the data volume is still small.

## Decision

**Every table uses a UUID v7 primary key**, changed in the same window as the tenancy migration. v7
is time-ordered, which keeps index inserts append-like (a random v4 scatters them) and makes ids
sortable by creation. Ids are generated by the application, not by the client's input: a client may
supply one for offline creation only where the specification for that feature allows it, with the
company scope still enforced.

## Consequences

- Every foreign key, the `AccessAccount`/`AccessProfile`/`Permission`/… tables and the `id` route
  params in `apps/api` (today parsed as numbers) change together.
- The mechanism that generates the value (Prisma's `uuid(7)` default if the pinned version supports
  it, otherwise the application) is settled in the specification after the Prisma upgrade.
- **The People grid's `Code` column breaks.** It shows `person.id.slice(0, 8)`
  (`person-columns.tsx`). In a v7 UUID the first eight hex digits are the top of a millisecond
  timestamp, so every row created within about a minute shares the same "code". Any identifier shown
  to a user needs its own human-readable value, not a slice of the key; sequential account and
  profile numbers that users quote today have the same need.
